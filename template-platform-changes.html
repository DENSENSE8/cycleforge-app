Templates became data — not a second app

A summary of what shipped and, more importantly, why it matters for the long term — how this turns a single-tenant tool into a sellable, multi-tenant, self-configuring ops platform.

Phases 1–5 complete Migration applied to Neon Curator review UI shipped Uncommitted on main

The change in one sentence: every way a workflow (an "ops SOP") can enter a tenant — the built-in library, an imported file, a shared community template, or an AI suggestion — now flows through one install path over durable Neon data, instead of code forks or a separate deployable app.

Before, onboarding silently activated a hard-coded graph and there were three slightly-different clone paths drifting apart. Now a tenant chooses its operating model at signup, templates are portable and curated, and AI can help — all without touching the engine, forking the app per customer, or ever storing a secret in a template.

The four invariants that make it durable

These are the load-bearing rules. Everything else is built so these can never be violated.

1

One clone path — installTemplateIntoOrg

System library, package import, onboarding, community submissions, and AI drafts all funnel through a single audited, tenant-scoped installer. No new "clone" logic is ever written again, so behavior can't drift between entry points.

2

Templates are Neon data, never a deployable app

A template is a graph + metadata rows — not a second service to run. The app stays a thin, stateless runtime. This is what keeps hosting cheap and lets the catalog grow without shipping code.

3

Capability boundary: reference only, never invent

A template may only reference registered node and surface types. New capabilities still require a platform pull request. So a tenant (or an AI) can compose the building blocks but can never smuggle in unreviewed behavior.

4

Nothing custom auto-activates

Imports, submissions, and AI drafts always land as a draft a human reviews and publishes. The blast radius of a bad template is zero until someone approves it.

How every template now enters a tenant

System library Package import Community submission AI draft → validate against registry → installTemplateIntoOrg → draft (or system → live)

One waist. The registry check + the single installer are the only way in — which is exactly why the safety rules above hold automatically.

What shipped, phase by phase

Phase 1

Template-first onboarding

Done

Signup no longer auto-seeds a hidden workflow. A new org has no active operation until the owner picks a template at /onboarding/template (the blessed default is pre-selected).

Long termThe product configures itself per vertical without code. This is the precondition for self-serve SaaS — a new customer models their shop by choosing, not by us writing a bespoke setup.
Phase 2

The single install path + correct surface wiring

Done

Collapsed three divergent clone routines into installTemplateIntoOrg, and fixed the join so a template's nodes seed the right operator screens (receiving → unbox, inspection → test, pack, ship).

Long termEliminates the highest-risk source of rot: parallel copies of critical logic. Every future feature inherits correct tenant-scoping, auditing, and surface-seeding for free.
Phase 3

Portable template packages (v1)

Done

A tenant can export any of its workflows to a self-describing CycleForgeTemplatePackage and re-import it. Import validates every referenced type against the live registry, then lands a draft.

Long termTemplates become transferable assets — between tenants, environments, and repos — with a hard compatibility contract. Foundation for backups, staging→prod promotion, and the shared catalog.
Phase 4

Curated community catalog — submit → review

Done + UI

New DB columns (visibility, review_status) track a moderation lifecycle. An org can submit its own workflow for the public catalog; a curator (new studio.catalog.review permission) approves or rejects it. A dedicated review workbench at /studio/catalog is the moderation surface.

Long termA network effect and moat: proven SOPs from real shops become shareable, vetted starting points. The more tenants, the richer the catalog — and curation keeps it trustworthy.
Phase 5

AI intake — constrained & safe

Done

A recommender ranks existing templates against a free-text description of the shop (it can only return real slugs). A closed "vocabulary" endpoint hands an AI exactly the registered node/surface palette it may draft with, plus a defense-in-depth pass that strips anything off-palette.

Long termAI leverage without AI risk: suggestions are bounded by the capability registry and never auto-activate. We can lean on models to accelerate setup while the safety boundary stays mechanical, not trust-based.

Why this is strategically important (not just tidy)

🏢

Multi-tenant, sellable

Per-vertical configuration lives in data, so onboarding a new paying tenant needs no code and no fork. This is the difference between a tool and a product.

🛡️

Safe by construction

The registry gate + single installer + draft-only rule mean new template sources can be added later and automatically inherit the safety guarantees.

🌐

Compounding catalog

Every tenant's best practices can become a curated, clonable template. Value grows with the customer base instead of staying flat.

🧩

Cheap to operate

No second server, no per-tenant deployment. The app remains a thin stateless runtime over Neon — the operating model scales without ops overhead.
