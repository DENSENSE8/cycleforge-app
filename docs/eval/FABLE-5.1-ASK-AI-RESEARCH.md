## B. Measured Ask architecture (live code, not the plan)

### B.1 The route — `src/app/api/assistant/chat/route.ts`

- Gate: `withAuth(..., { permission: 'assistant.chat' })`; per-org rate limit `ASSISTANT_CHAT_RATE_LIMIT || 25` per minute (`route.ts:165`); body is `{ sessionId, message ≤4000, context{page, station, mode, selection, skill ≤4000} }` — org/staff/permissions come from `ctx`, never the body. `maxDuration = 300` (`route.ts:21`).
- **Brain split (measured, not as the plan describes it).** `route.ts:189`: `const skillNeedsTools = /\bpropose_mutation\b/.test(context?.skill ?? '')`. `route.ts:196`: `brain = grokConfig && !skillNeedsTools ? null : await resolveOrgAnthropicBrain(orgId)`. `route.ts:208`: `useHermes = (grokConfig !== null && !hasAnthropic) || ((forceHermes || !hasAnthropic) && fallbackConfig !== null && reachable)`.
  Consequence: the classifier trace shows `UNBOX_SKILL` and `SHIPPING_ORDERS_SKILL` both contain `propose_mutation` (`skillNeedsTools_unbox: true`, `skillNeedsTools_shipping: true`; `STATION_SKILL: false`). So on the two surfaces where Station Ask actually mounts (Unbox and To-ship):
  - with any Anthropic key present (org vault or platform `ANTHROPIC_API_KEY`), **every** turn goes to the Anthropic loop, including the packing-count question — Grok is never the mouth there;
  - with no Anthropic key, `brain` is null, `useHermes` is true via Grok, and the model receives a skill telling it to call `resolve_item_number` / `propose_mutation` **while being advertised zero tools**.
  The plan's §2 diagram ("Grok connected, skill has no propose_mutation → streamHermesCompletion") is accurate as a rule; what it under-states is that both Ask pages trip the rule.
- **Grok path** = `streamHermesCompletion` (`route.ts:85`): one `POST {baseURL}/chat/completions` with `aiRequestHeaders(config, {'X-Hermes-Session-Id', 'X-Source':'assistant'})`, body `{ model, stream: true, messages: [system, user] }`, `AbortSignal.timeout(120_000)` (`route.ts:121`). The reader only looks at `choices[0].delta.content` (`route.ts:146`). **No `tools`, no `tool_calls` parsing, no history** — the history loaded by `loadAssistantHistory` (limit 20, `chat-persistence.ts:25`) is passed only to `runAssistantTurn`, so Grok gets a single-turn conversation every time.
- **Anthropic path** = `runAssistantTurn` (`agent-loop.ts`), advertised `listAssistantTools(ctx)` + permission-filtered write tools + `UI_TOOLS`, emits `delta` / `tool` / `ui_tool` / `error` SSE.
- **Pre-loop** (`route.ts:257` → `enrichAssistantTurn`), order in `enrich-turn.ts`: carton brief if a receiving is selected and `isCartonAskQuestion` (`:142`) → `classifyOrgChatQuestion` (`:146`) → `resolveLocalAiAnswer` (`:151`, canned reply short-circuits **both** brains at `route.ts:266`) → generic `detectIntents` + `enrichAssistantMessage`.
- Voice overlays `CARTON_ASK_SYSTEM` / `ORG_CHAT_SYSTEM` are applied **only** on the Hermes/Grok branch (`route.ts:274`); the Anthropic loop ignores `prepared.voice`.

**Can Grok call tools today? No.** Proof: `streamHermesCompletion` sends no `tools` key and reads only `delta.content`; the only tool loop is `runAssistantTurn`, which is Anthropic-SDK-native (`client.messages.stream({ tools })`, `stop_reason === 'tool_use'`), and `resolveOrgAnthropicBrain` (`org-provider.ts:281`) deliberately excludes OpenAI-wire providers ("the agent loop uses Anthropic's native tool-use API").

### B.3 Enrichment — `enrich-turn.ts`, `org-chat-facts.ts`, `carton-ask-brief.ts`

Utterance is classification-only; SQL is a closed template `packCountSql(scopedToPacker)` with `$1 org`, `$2 staff`, `$3/$4 dates`; the staff row is checked `id + organization_id`; a null `ctx.staffId` yields "No packer is signed in".
- Hard-coded timezone: `timezone('America/Los_Angeles', pl.created_at)::date` (`org-chat-facts.ts:65`), `resolveAiTimeframe` returns `timezone: 'America/Los_Angeles'` for every kind (`date-range.ts:55`), and the pool itself is started with `options: '-c timezone=America/Los_Angeles'` (`src/lib/db.ts:64`). `warehouses.timezone` exists per org (`2026-05-14_multi_warehouse.sql:19`, `src/lib/warehouses.ts:9`) and is not consulted.

Raw `pool.query('SELECT 1')` = 83–96 ms; `tenantQuery('SELECT 1')` = 340–696 ms; three queries on **one** `withTenantConnection` client = 553 ms. Prod (Vercel us-east-1) shrinks the constant, not the multiplier.

### B.7 SuperGrok — `src/lib/integrations/grok/oauth.ts`

- Proxy base `https://cli-chat-proxy.grok.com/v1`, default model `grok-4.6`, headers `X-XAI-Token-Auth: xai-grok-cli`, `x-grok-model-override`, `x-grok-client-version` (`GROK_CLI_VERSION = '1.0.13'`, `:125`; missing → HTTP 426 per `:123`), `x-grok-client-identifier: grok-shell`, `User-Agent xai-grok-cli/…`. `ensureGrokChatConfig` (`:424`) refreshes inside the 5-minute skew, persists rotated refresh tokens, and falls back to a still-live access JWT when the refresh was already spent by the host CLI. `MANAGED_AI_HOSTS` includes the proxy (`provider.ts:193`), so `chat_template_kwargs` is never sent to it.
- Host evidence (`~/.grok/models_cache.json`, fetched by the CLI on 2026-09-05 from `…/v1/models`, `grok_version 1.0.13`): both `grok-4.6` and `grok-4.5` report `"api_backend": "responses"`, `"stream_tool_calls": null`, `context_window 500000`, `reasoning_effort "high"` with `supports_reasoning_effort true`. `~/.grok/README.md` line 397 shows the proxy accepting `POST /v1/chat/completions` (`grok-build`, `stream: true`) and states "Most models behind the proxy only support streaming." The July-2026 wire-level gist of Grok Build confirms the official client's inference call is `POST /v1/responses`. ### C.2 Decisions

**Q1 — Semantic catalog, not row embeddings.** Side with the catalog (pgai, Wren, Cube, dbt all embed *meaning*; the structured-RAG literature says "use SQL for current rows, RAG for schema/metadata"). Why row embeddings fail on "packages this packer this week": the answer is a **COUNT over a filtered window**; nearest-neighbour retrieval returns k *documents* that look like the question, it cannot sum, cannot bound a date window, goes stale on every scan (`packer_logs` is append-only all shift), and the tenant filter becomes a metadata tag on a vector rather than a Postgres policy. The measured classified COUNT is 0.034 ms of execution against a FORCE-RLS table. Embeddings belong on **descriptions + examples** (§19) and on **entity documents** (`entity_search_docs`, already org-led).

**Q2 — Where embeddings live in a pooled multi-tenant app: both, tagged by column not namespace.** Catalog rows are platform-owned (`organization_id NULL`, hand-written FORCE policies as in `insight_links`), entity docs are org-led (`organization_id NOT NULL`, unique per org). Serious products tag tenancy the same way — Wren binds `organization_id` as a session property, Snowflake pins immutable session attributes, Databricks/Unity enforces row filters — none put the tenant in a vector namespace. Optional per-org synonym rows later ride the same table as org-stamped rows.

**Q3 — Stopping cross-tenant SQL, ranked for Cycle Forge.**
1. Session GUC + FORCE RLS — `withTenantConnection` (`SET LOCAL` via `set_config(…, true)`), every wave-1 table `rls_forced: true`. This is the backstop and it is already live.
2. Explicit `organization_id = $n` in every helper SQL (house law D5; `org-chat-facts.ts` does it; `upsertOrderAssignment` and `setOrderFlag` do not on their reads — §D, gap E4).
3. CTE pre-filter (PAR "split-plane") — for us this is the typed helper itself; nothing to add.
4. AST rewrite injecting `org_id` (agent-sql) — only for the optional read-only hatch (§8), never for the default path.
5. Per-user DuckDB slice (Relta) — refuse: a copy per turn, stale, and a second engine.

**Q4 — Writes are never free SQL.** Relta (read-only sandbox), Wren (query), Vanna (analytics), agent-sql ("Only SELECT… impossible to insert, drop or anything else"), object-capability (SELECT), Oracle (generate only; execute under the user's DB permissions). Cycle Forge's `MUTATION_KINDS` + `applyAgentMutation` is stricter than all of them (named kinds, trust class, permission copied from the UI route, inverse captured). Keep it; the industry has no write plane to steal.

**Q5 — OpenAI-wire tool loops on Grok/xAI.** xAI documents Chat Completions tool calling (`tools[]`, `tool_choice auto|required|none`, `parallel_tool_calls`, results as role-`tool` messages with `tool_call_id`) and the Responses API (`function_call` output item `{call_id, name, arguments}`, results as `function_call_output`, `previous_response_id`), and states "With streaming, the function call is returned in whole in a single chunk, not streamed across chunks." Anthropic `tool_use` is a different protocol; nothing in `agent-loop.ts` transfers except the loop skeleton and the dispatch. Risks specific to `cli-chat-proxy.grok.com`: (a) the official client uses `/v1/responses` and the models cache says `api_backend: "responses"` — `/chat/completions` + `tools` is unproven on the proxy; (b) "most models behind the proxy only support streaming"; (c) OpenAI-compatible relays are known to emit `tool_calls` with a non-zero starting `index` (vercel/ai#18333) and `finish_reason: "stop"` after tool calls (open-webui#21768) — accumulate by `index` in a `Map`, and treat any accumulated call with a name as a tool round regardless of `finish_reason`; (d) reasoning is on by default (`reasoning_effort: high`) — first-token latency; (e) 7-day session tokens and rotated refresh tokens — a 401 mid-loop must refresh once; (f) `x-grok-client-version` drift → 426.

**Q6 — Latency.** Production NL→data systems land at ~8 s average with a 67 % semantic-cache hit rate; semantic-cache lookups cost 8–80 ms; nobody publishes sub-2 s with an LLM deciding the query. Sub-2 s therefore means: no LLM decision (Layer 1 classifier → one parameterized query → one short streamed sentence), or at most **one** tool round with ≤12 advertised tools. Measured here, SQL execution is not the cost — the tenant wrapper's four round trips are (340 ms vs 0.03 ms), and identifier search fans out to 19 queries (1.2 s). Keeping Layer 1 is supported; the biggest local lever is **one tenant connection per turn** (§22), not fewer SQL statements.

**Q7 — Metric layer vs typed tools.** Decision: **in-repo catalog + typed tools; do not deploy Cube or Wren for 12 months.** Reasons: (1) the 34 existing tools already are "measures and dimensions by name"; (2) Cube/Wren have no write plane and Ask's value is CRUD under the UI's permissions; (3) both would need a second copy of tenant security context and a second service to keep alive next to `:3050`; (4) the dbt benchmark shows the accuracy jump comes from *modelling* (three models), which a TS catalog with descriptions and examples delivers without a server; (5) Cube Core is Apache-2.0 and self-hostable, so if Ask ever needs ad-hoc slicing across 100 metrics the door stays open. Revisit when the catalog exceeds ~40 metrics or when a customer asks for BI, not chat.

**Q8 — MCP as the execute plane.** Decision: **in-process registry.** Ask's Grok loop calls `runAssistantTool` / the shared write dispatch directly; `src/lib/mcp/tool-server.ts` stays the second transport for external clients over `/api/mcp`. Oracle's generate/execute split exists to cross an identity boundary; inside one Next.js process the boundary is `ctx`, and a JSON-RPC round trip would add serialization and a second permission surface for nothing. The one thing to keep from Oracle: execution runs under the caller's identity (`ctx`) with the store's permissions (FORCE RLS), which is already true.

### D.3 Gaps this list missed (found in code)

- **E1 (P1) — Timezone is hard-coded to America/Los_Angeles** in the classified COUNT (`org-chat-facts.ts:65`), `date-range.ts:55`, the pool (`db.ts:64`), `enrich-message.ts`, and `get_packing_kpi` ("Pacific calendar day"). ### F.2 Buy vs build, in one paragraph

Build the catalog in-repo and keep typed tools; do not buy Cube or Wren. The two things a semantic-layer product sells — governed metric definitions and compile-time tenant injection — Cycle Forge already has in a stricter form (`MUTATION_KINDS`/typed tools for the vocabulary, FORCE RLS + `SET LOCAL` for the tenant), and neither product has a write plane, which is where Ask's value is. The dbt 2026 benchmark shows the accuracy gain comes from modelling, and three well-described entries lifted both approaches by 30–40 points; a reviewed TypeScript catalog with descriptions, joins, metrics and examples delivers that modelling without a second service, a second security context, or a per-seat bill. Cube Core stays a credible option if Ask ever needs ad-hoc slicing across dozens of metrics — that is a 2027 question.
